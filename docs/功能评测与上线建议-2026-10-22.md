# PortGuard v1.2.0 整体功能评测与上线建议

- 评估日期：2026-10-22
- 评估基线：`e41eb79`（v1.2.0，界面优化第二轮完成）
- 评估视角：**功能完整性 + 7×24 长期稳定 + 安全防护**（按「能不能真上线」的标准看，不按「功能有没有」看）
- 评估方式：源码精读（core / app / gui 共 23 898 行）+ 四道门禁实测 + 只读命令核查
- 未覆盖：真机防火墙写操作（本轮进程非管理员，`IsUserAnAdmin=False`），该验证属 `tools/verify_firewall.py`，需 UAC 手工跑一次

## 1. 结论先行

### 1.1 五维打分

| 维度 | 得分 | 一句话判断 |
|---|---|---|
| 功能完整性 | **4.0** / 5 | 「发现 → 判定 → 封禁 → 到期解封 → 对账」闭环完整，且**每一环都有失败可见化**；缺的是多机、报表、远程告警这类「规模化」能力 |
| 长期稳定性（7×24） | **3.0** / 5 | 数据层与采集层能扛；**阻塞点在进程自身**：UI 线程直接跑外部命令、攻击高峰时表格全量重建、进程不在时封禁永不解除 |
| 安全防护 | **4.0** / 5 | 注入面已系统性封堵并有实测用例；v1.2.0 删掉 HTTP 上报后**攻击面从网络收敛到本机输入**，这是最大收益。扣分在「全进程高权限」「产物无签名」「敏感数据明文」 |
| 工程质量 | **4.5** / 5 | 四道门禁全绿、双栈差异收口、注释记录「为什么这么写」。这是同类单机工具里罕见的水平 |
| 可运维性 | **2.5** / 5 | 界面已经很能看，但**没有开机自启、没有崩溃看护、没有远程告警、没有自动备份** —— 无人值守场景等于「装了个需要人盯的工具」 |

**综合 3.6 / 5。**

### 1.2 一句话结论

> 核心能力与代码质量已经达到可交付水准，**风险全部集中在「它得一直活着、并且有人知道它出了什么事」这一层**。
> 有人值守、内网单机、管理员常驻的用法今天就能上；**无人值守或多台部署，必须先补完 §5 的 5 项 P0**。

### 1.3 最该先做的三件事

1. **攻击高峰时事件页会卡死**（`gui/mixins.py:173` + `gui/page_events.py:748`）：每条风险事件到达即全表重建。**实测（离屏，200/500/2000 行）单次刷新分别 358 / 936 / 4143 ms**，而事件泵节拍是 **150 ms** —— 即便只有 200 行档位，渲染耗时也是节拍的 2.4 倍，**入不敷出**。攻击时事件成批到达，界面只会越来越滞后。**在最需要看界面的时刻界面最卡**。
2. **到期巡检跑在 GUI 线程**（`gui/mixins.py:125` → `app/ban_service.py:635` → `core/firewall.py:447`）：每条到期封禁都要起 2~3 个 `powershell` / `netsh` 子进程，`unblock_ip` 内部还会列一次全量规则。30 条到期 ≈ 30 秒~2 分钟界面假死，用户会以为程序崩了而强杀 —— 强杀又留下未解封规则。
3. **进程不在 = 封禁永不解除**：Windows 防火墙规则本身没有到期时间（`core/firewall.py:196-218` 注释已说明），到期完全靠进程内 60 秒巡检。程序关掉、崩溃、机器重启后没自启 —— 那些规则**永久生效**，且没人会收到通知。

## 3. 功能评测

### 3.1 核心闭环：完整且失败可见

| 环节 | 实现 | 失败时用户能看到什么 |
|---|---|---|
| 采集（双通道） | `core/port_watcher.py` + `core/win_net.py` / `core/win_fwlog.py` | 通道异常计数、最后错误、日志偏移 |
| 归属地 | `core/geo_locator.py`（离线 xdb，LRU） | 「未知」而不是猜境内/境外 |
| 判定 | `core/rule_engine.py`（9 条内置 + 区域规则） | 命中规则名 + 逐条得分 |
| 落库 | `core/db_writer.py`（单写线程攒批） | 队列满显式 `dropped` 计数，不静默丢 |
| 封禁 | `app/ban_service.py` → `core/firewall.py` | **三重校验**：命令返回 0 + 规则回读 + 防火墙确实开启 |
| 到期解封 | 60 秒巡检 | 无管理员时限流告警 + `expired_backlog()` 数字 |
| 对账 | `ban_service.reconcile` / `reenforce_all` | 空规则列表先二次确认，避免误标已解封 |

**这是本产品最值钱的部分**：安全工具最坏的失败形态是「显示已防护、实际没有」，而这条链路每一处都在防这件事。

### 3.2 v1.2.0 相对 v1.1.0 的实质进步

| 变化 | 意义 |
|---|---|
| 删除 HTTP 上报服务 / API Key / Webhook | **网络攻击面归零**。原来 S1（时间戳伪造）、S2（IP 伪造）、S4（无限流）、S5（Key 写日志）四类风险随之消失，不再是「待修」而是「不存在」 |

| 一个 IP 恒定一条规则（`core/firewall.py:114`） | 修掉真机上「解封了还封着」和「规则越滚越多」两个反向事故 |
| 防火墙关闭时判失败（`core/firewall.py:383`） | 修掉最隐蔽的假成功 |
| 操作审计 + 四张表各自保留期 | 从「无账本」到「谁在何时封了谁」，且审计表自己也有保留期 |
| 历史访问检索 / 导出 / 数据库维护 / 关于页 | 运维刚需补齐 |

## 4. 长期稳定性专项（7×24）

### 4.1 设计上已经做对的（不必再投入）

- **写入路径有界**：单写线程 + 攒批（200 条 / 200ms）+ 队列 20 万 + 满时显式计数；SQLite 单写者天然消除 `database is locked`。
- **高频读缓存**：`core/settings.py` 进程内缓存 + 写时失效，判定链上不再反复查库。
- **窗口有上限**：规则引擎滑动窗口 5000 条 / 300s，防 O(n²)。
- **去重表有清理**：`port_watcher._dedupe` 超 5 万条按窗口裁剪。
- **日志双保险**：按天滚动 + 单日 5MB 兜底 + 同名归档加序号 + 目录不可写降级 `NullHandler`（`core/logger.py:80-132`）。
- **四张表都有保留期**，且**刻意不合并**（流水 30 / 事件 90 / 封禁 180 / 审计 180）。
- **数据库备份用 `Connection.backup()`** 而不是 `copy2`（WAL 下 `copy2` 会丢最后几批）。
- **恢复流程有顺序约束**（暂存 → 备份当前库 → 停写入器 → replace → 清 `-wal/-shm` → 迁移 → 重启写入器）。
- **防火墙日志文件被重建时**（size < offset）能自动从头读。

> S1 / S2 是「用户会以为程序坏了」的那类问题，优先级高于任何新功能。

#### S1 实测数据（本轮离屏量取，`QFont 10pt`，1360×780）

| 行数档位 | `EventsPage._render` 单次耗时 | 事件泵节拍 | 结论 |
|---|---|---|---|
| 最近 200 条 | **358 ms** | 150 ms | 渲染 2.4× 于节拍，已入不敷出 |
| 最近 500 条 | **936 ms** | 150 ms | 6.2× |
| 最近 2000 条 | **3426 / 4143 ms** | 150 ms | 23~28× |

拆解同一规模（2000 行 × 11 列）的裸 `QTableWidget` 开销：`setItem` 全列 **111 ms**，再叠加 2000 个行内 `setCellWidget`（每行 2 个按钮）**+580 ms**。也就是说：690 ms 是「表格下限」，剩下 **2.7 秒**来自 `make_item` 逐格构造、`_row_actions` 每次新建控件、`CheckMarkDelegate` 与勾选模型的同步。

**修复优先级因此很明确**：
1. 行内按钮改 `QStyledItemDelegate` 绘制 + 点击命中（省 0.6 秒/2000 行，且不再随行数线性创建对象）；
2. 刷新节流：`_drain_events` 里对事件页改为「标记脏 + ≥1 秒最多重渲染一次」，风险事件只更新计数与状态栏；
3. 攻击期间自动降档到 200 条并提示「已临时降低显示条数以保持界面响应」。

### 4.4 需写进运维 SOP 的取舍（不是 bug）

1. **程序停 = 不解封、不巡检、不告警**。必须在部署文档第一页写明。
2. **`synchronous=NORMAL`**：断电可能丢最后几批日志（不会损坏库）。安全监控可接受，但要写清。
3. **采集只能看见「存活连接」+「防火墙日志窗口」**：极短连接若既没进日志窗口又没被抓到采样点，会漏。当前 5 秒采样 + 双通道已是最优折中。
4. **防火墙日志滚动窗口有限**：高频攻击下旧记录会被覆盖。

### 5.2 安全缺口（按可利用性排序）

| # | 缺口 | 证据 | 风险 | 建议 |
|---|---|---|---|---|
| **A1** | **全进程 `requireAdministrator`** | `app.manifest` + `port_guard.spec:156` | 界面、解析、渲染、CSV 导出的任何一处内存/解析缺陷，都以 SYSTEM 级权限执行；违背最小权限原则 | 中期拆成「普通权限 UI + 高权限代理进程（只暴露 block/unblock/list 三个动词，用本地命名管道 + 消息结构校验）」。成本中，但这是安全工具该有的架构 |
| **A2** | **配置文件低权限可写 + 程序高权限读取** | `core/config.py:118-125`（`%APPDATA%\PortGuard`，普通用户可写）、`data/rules.json` | 提权链的经典形态：低权限用户改规则/黑名单 → 高权限程序加载。当前解析侧都有校验（`normalize_ip`、字段白名单），**不构成可直接利用的漏洞**，但属于「设计上不该有的信任边界」 | 数据目录迁 `%ProgramData%\PortGuard` 并设 ACL（Administrators 完全控制、Users 只读）；或用户级配置与策略级配置分离 |
| **A3** | **产物无签名、无完整性校验** | spec 未配置 Authenticode；只有 zip 的 SHA256 | 分发环节被替换/篡改无法发现；SmartScreen 会拦 | ① 代码签名证书签 exe；② 启动时校验 `_internal` 关键 DLL 的哈希清单；③ README 里给出「如何核对 SHA256」 |
| **A4** | **敏感数据明文** | SQLite 明文（IP + 归属地 + UA + 访问路径）、`logs/portguard.log` 同样内容、CSV 导出无脱敏 | 属个人信息/行为数据；一旦机器被入侵或文件外流，等于直接泄露 | ① 库与日志目录 ACL 收紧；② 加「脱敏导出」选项（IP 掩码 / 去掉 UA）；③ 文档给出保留期依据（已有 30/90/180/180） |
| **A5** | **审计可被本机高权限篡改** | `audit_log` 是普通表，程序自己有权 `DELETE` | 「谁解封了谁」在管理员作恶时不可信 | 单机工具的合理上限；若要更强：审计行加 HMAC 链（前一行哈希），或导出到只追加的外部通道 |
| **A6** | 单实例互斥体名字固定 | `core/single_instance.py:26`（`Local\` 会话级） | 同会话内任意进程可先创建同名 mutex → 拒绝服务（低危，只是起不来） | 可接受；若在意，加「同名实例探活 + 二次确认启动」 |
| **A7** | `--diag` / `--enable-firewall` 靠 `in sys.argv` 判断 | `main.py:272,291` | 拼错参数会静默进 GUI（v1.1.0 已提，未改） | 改 `argparse` |

### 5.3 威胁模型小结

v1.2.0 的攻击面已经很小：

- **网络面**：无监听端口 → 远程无法直接攻击本程序。
- **本机面**：输入只有「IP 输入框 / 黑名单文本 / 规则配置 / 离线库 URL」，四条都有白名单；命令行拼接全部经过 `ps_quote`。
- **权限面**：整个进程高权限（A1）是唯一的结构性风险。
- **分发面**：无签名（A3）是唯一可被第三方利用的环节。

## 8. 长期运行 SOP（建议随产品交付）

**每日**：看顶栏「防火墙」项是否为「域/专用/公用 全开」；看状态栏是否有「有 N 条封禁已到期但无权限」。

**每周**：看设置页「数据库维护」的库大小与备份列表；看审计页有没有非预期的解封。

**每月**：手动 VACUUM 一次（大批量清理后必做）；核对防火墙控制台里 `PortGuard_Block_*` 条数与封禁页 active 条数是否一致（不一致就点一次「对账」）。

**异常处置**：
- 界面卡住 → 先看任务管理器 CPU，**不要直接强杀**（强杀会留下未解封规则）；等 1~2 分钟，或在另一台机器上远程看日志。
- 怀疑误封 → 封禁页搜 IP → 先「解封」再查原因，别直接删记录（删记录不解封）。
- 重装/换机 → 先导出黑名单，再保留 `%APPDATA%\PortGuard\backup` 下的 `.bak`。
