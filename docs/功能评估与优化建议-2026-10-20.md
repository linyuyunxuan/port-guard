# PortGuard v1.1.0 功能评估与优化建议

- 评估日期：2026-10-20
- 评估基线：`5521d03`（`ui: 全局视觉与组件层重设计`）
- 评估方式：源码精读 + 只读命令核查（`ls/du/git/stat/grep`）+ 离屏探针，未执行打包
- 结论性质：功能与工程层面的**静态评估**；防火墙写操作只做代码路径审查，未实机验证（该验证属 `tools/verify_firewall.py` 的职责，需 UAC）

---

## 1. 结论先行

### 1.1 五维打分

| 维度 | 得分 | 一句话判断 |
|---|---|---|
| 功能完整性 | 3.5 / 5 | 核心「发现 → 判定 → 封禁 → 解封」闭环完整且边界扎实；但**查询/导出/告警/审计**这一整层运维能力几乎空白 |
| 安全与可靠性 | 4.0 / 5 | 命令注入面已被系统性封堵，异常路径归因清晰；短板是**上报侧时间戳与 IP 可伪造**、**自动封禁缺去重** |
| 性能与容量 | 3.5 / 5 | 写入路径（单写线程攒批 + 滑动窗口上限）设计良好；`risk_event` 无保留期、关键词检索全表扫、事件页全量重建是三处现实隐患 |
| 工程质量 | 4.5 / 5 | 分层清晰、双栈（PySide2/PySide6）差异全收口、四道静态门禁严格；**GUI 层 0 单测**、CI 不跑交付栈是缺口 |
| 运维体验 | 3.0 / 5 | 批量操作与时间筛选刚补齐；危险操作确认框的**默认按钮与红色语义不一致**、多处文案与行为不符 |

**综合**：工程质量明显优于同类单机工具，是一份「能放心改」的代码；产品层面处在**「能用」但「不好交付」**的阶段——核心功能可信，运维闭环缺失。

### 1.2 最该先做的三件事

1. **规则保存静默丢参数**（已修，见 §7.1）：运维在规则页点一次「保存并生效」，`sensitive_path_login.paths/status`、`scanner_ua.empty_ua` 三个命中条件被删除，规则仍在、开关仍开，但**永远不再命中且不报错**。
2. **自动封禁无去重**（`core/pipeline.py:32-61`）：开启自动模式后同一 IP 会重复建 `pending` 记录并**重复创建防火墙规则**。
3. **交付产物缺失**：`dist/PortGuard` 是空目录（上次构建前被移走后未重建），当前**没有可交付的 exe**。

### 1.3 两处「名不副实」（别当成已实现能力）

- 规则级 `level` / `action` **不影响判定**：等级由总分映射（`core/rule_engine.py:568-578`），`suggest_ban` 也由等级推出（`:562`），但规则页把它们做成可编辑控件（`gui/page_rules.py:50,107-128`）。
- `stats_hourly` 表有建表无读写（`core/database.py:135-140`）、`ban_list.unblocked_by` 有列无写入点（`core/database.py:615`）、`SOURCE_LABEL["suggest"]` 无产生方、`PORTGUARD_NO_UPDATE`（`core/config.py:270`）无读取点。

## 2. 功能完整性

### 2.1 核心链路：闭环 ✅

| 环节 | 入口 | 证据 |
|---|---|---|
| HTTP 上报 | `report` → `_process` → `process_record` | `core/report_server.py:302,195,207` |
| 本机自采 | TCP 连接表 + 防火墙日志双通道 | `core/port_watcher.py:376`、`core/win_net.py`、`core/win_fwlog.py` |
| 归属地 | `get_locator().lookup` | `core/pipeline.py:106` |
| 规则打分 | `evaluate`，逐条累加封顶 100 | `core/rule_engine.py:417,560` |
| 入库 | 单写线程攒批，access/risk 同事务 | `core/db_writer.py:86,173,181-185` |
| 人工确认 | `request_ban`（唯一校验入口） | `gui/main_window.py:747`、`app/ban_service.py:45` |
| 写防火墙 | PowerShell + netsh 回退 | `app/ban_service.py:71` → `core/firewall.py:130` |
| 解封 / 到期 / 对账 | `unban` / 60s 巡检 / `reconcile` | `app/ban_service.py:128,162,191` |

两条采集通道共用同一 `pipeline`，不会出现「同一 IP 两种结论」。

### 2.2 九条内置规则语义

| 规则 | 触发条件 | 分 | 实际等级 | 类型 |
|---|---|---|---|---|
| `blacklist` | 命中黑名单（支持 CIDR） | 100 | critical | 单次 |
| `port_scan` | 30s 内不同端口 ≥15 | 80 | high | 窗口 |
| `sensitive_path_login` | 60s 内敏感路径 401/403 ≥10 次 | 70 | high | 窗口 |
| `geo_sensitive_port` | 管理端口 + 归属地命中 `geo_scope` | 65 | high | 单次 |
| `rate_limit` | 10s 内 ≥50 次 | 60 | medium | 窗口 |
| `scanner_ua` | UA 命中特征或为空（限 HTTP 上下文） | 45 | medium | 单次 |
| `error_storm` | 60s 内样本 ≥20 且错误率 ≥0.7 | 40 | medium | 窗口 |
| `suspicious_method` | TRACE/PUT/DELETE/CONNECT/PATCH | 30 | low | 单次 |
| `large_body` | 单次 ≥5MB | 25 | low | 单次 |

**刻意保守的设计**（不要当 bug 改）：
1. 白名单最高优先，命中即 0 分且永不封禁（`core/rule_engine.py:423-431`）
2. 内网/回环/保留地址三处独立拦截（`core/config.py:56-72`、`core/rule_engine.py:113-117`、`app/ban_service.py:55-56`、`core/firewall.py:145-148`）
3. 归属地「未知」不判为境内也不判为境外（`:495`、`:355-371`）
4. 「UA 为空 = 扫描器」只在 HTTP 上下文生效，避免自采 TCP 记录白拿 45 分（`:120-134,516`）
5. 窗口硬上限 5000 条 / 300s，防 O(n²)（`:41-47,195`）
6. 自动封禁三重闸门且**默认关闭**，本机采集默认不允许触发（`core/pipeline.py:144-150`、`core/port_watcher.py:115`）
7. 单次 sqlmap 探测只告警不封禁；12 次 `/admin/login` 401 才到 100 分

### 2.3 页面能力清单

| 页面 | 筛选 | 批量 | 导出 | 条数上限 | 主要缺口 |
|---|---|---|---|---|---|

| 规则配置 | ❌ | ❌ | ❌ | — | 规则不可增删；`level`/`action` 无效；黑白名单只能整块文本编辑 |

### 2.4 缺失的运维能力（P2，排期用）

- 事件 / 封禁 / 访问记录**导出**（唯一 CSV 在 IP 查询页 `gui/page_iplookup.py:286-314`）
- **外部告警通道**：只有声音 + 托盘气泡 + 弹窗（`core/alerts.py:81-88`），无人值守等于没告警
- **操作审计**：无审计表；解封人字段空置，无法回答「谁在何时解封了谁」
- **历史访问检索**：`query_access_logs`（`core/database.py:367`）零调用，只能看内存环形缓冲
- 策略化封禁时长（按等级/规则给不同时长、递增封禁）
- 数据库维护入口（`vacuum` 未接 UI）、离线库**回滚**入口（`core/xdb_updater.py:551,573` 未接 UI）
- 关于页 / 快捷键帮助 / 列排序 / 配置导入导出 / 深浅色主题

## 3. 安全与可靠性

### 3.1 已做扎实的 ✅

- **命令注入**：IP 前置白名单（`core/validators.py:53-94`）、PowerShell 单引号字面量（`:110-120`）、规则名白名单+前缀强制（`:123-137`）、`netsh` 一律列表传参（`core/firewall.py:167-181`）；解封只允许删 `PortGuard_Block_` 前缀（`:193-198`）
- **默认收敛**：只听 127.0.0.1（`:22`）、`/docs` `/redoc` `/openapi.json` 全关（`:230-236`）、CORS 默认不加、非回环且未设 Key 时**强制生成 API Key**（`:388-409`）
- **洪水防护**：令牌桶 300/s burst 600、body 2MB、批量 ≤1000、窗口 5000 上限、写队列 20 万 + `dropped` 显式计数——整体有界
- **启动失败归因**：端口占用/权限不足/internal 三分类 + 可执行建议（`core/report_server.py:95-121,141-157`）

### 3.2 待修风险

| # | 风险 | 证据 | 影响 |
|---|---|---|---|
| S1 | **客户端时间戳可伪造**：窗口规则以 body 里的 `timestamp` 为「现在」，该值还决定保留期删除边界 | `core/rule_engine.py:420,453`、`core/models.py:59-82`、`core/database.py:415` | 伪造旧时间戳 → 窗口永不累积，4 条窗口型规则全废 |
| S2 | **IP 可伪造**：body 的 `ip` 覆盖 TCP 来源，而 API Key 默认为空即放行 | `core/report_server.py:197-203,250-253` | 本机任意进程可写任意 IP 的风险分 |
| S3 | **自动封禁无去重** | `core/pipeline.py:32-61` vs `app/ban_service.py:90-97` | 规则名带随机后缀不互相覆盖 → 防火墙规则无限增长 |
| S4 | `/rules/reload`、`/banned/{ip}` 无限流 | `core/report_server.py:349,356` | 可反复触发重载；无 Key 时可探测「某 IP 是否被封」 |
| S5 | API Key 明文存库 + **自动生成时把完整 Key 写进日志** + 非常量时间比较 | `core/report_server.py:250-253,398-406` | 日志外泄即凭据外泄 |
| S6 | 防火墙日志路径来自设置且未校验 | `core/win_fwlog.py:409-424` | 非注入，属可滥用配置 |
| S7 | 删记录不删规则、对账只改库；对 `rule_name` 为空的记录跳过 | `core/database.py:788-803`、`app/ban_service.py:191-208` | 可能留下**无主防火墙规则** |
| S8 | 退出只等写线程 3s；`synchronous=NORMAL` | `gui/main_window.py:992`、`core/db_writer.py:9-22` | 断电/积压可丢数据（显式取舍，但应写进文档） |

### 3.3 权限降级行为不一致 ⚠️

无管理员时：封禁被拒（有提示）、**到期自动解封静默 return**（`gui/mixins.py:251-253`）。
→ 长期以普通权限运行，封禁账本会与防火墙**持续偏离**，且界面从未说明「到期也不会解封」。

## 4. 性能与容量

**做得好的**：热点写入单线程攒批（200 条 / 200ms）、只读短连接 + WAL、窗口有上限、监控页用 `QAbstractTableModel` 只渲染可见行（五张表里唯一能扛量的实现）。

**三处现实隐患**：

1. **`risk_event` 无保留期**：清理只作用于 `access_log`（`app/maintenance.py:25-35`），派生结论表永久增长；且 `count_risk_unhandled()` 每 2 秒全表 `COUNT`（`core/database.py:590-597`）
2. **关键词检索全表扫**：`%kw%` 前缀通配无法走索引（`:374-387`、`:515-525`、`:698-700`）；`ban_list.expire_at`、`risk_event.access_id` 无索引
3. **事件页全量重建行内控件**：`setCellWidget` 逐行创建（`gui/page_events.py:495`），2000 行 + 每次刷新重建，开销最重；且无列排序（`setSortingEnabled` 全场 0 处）

其他：`list_all_active_bans` 固定 `limit=100000`（`:731-732`）；删除不分批、清空日志不 VACUUM。

## 6. 运维体验（界面层）

### 6.1 危险操作的确认与红色语义不一致 ⚠️

| 操作 | 二次确认 | 默认按钮 | 红色 |
|---|---|---|---|
| 批量解封 / 批量删除记录 / 批量删除事件 | ✅ | 否 ✅ | 无 |
| **一键全部解封** | ✅ | **是** ⚠️ | 无（藏在「⋯」菜单） |
| **删除单条封禁记录** | ✅ | **是** ⚠️ | 无 |
| **删除区域规则 / 加入黑名单** | ✅ | **是** ⚠️ | 无 |
| 单条/批量封禁确认 | ✅ | Ok（是） | 红 |
| 停止接收服务 | **无确认** ⚠️ | — | **满底红** |
| 清空全部日志 | ✅ | 否 | 满底红 |

问题：破坏性删除类**全部无红**，反而「停止服务」是满底红——红色被读成「防护动作」而非「破坏动作」；4 处确认框默认「是」，回车即执行不可逆操作。

### 6.2 文案与行为不符（用户可感知的 Bug）

1. 「暂停滚动」实际是**停止接收并丢弃**新记录（`gui/page_monitor.py:335` vs `:498-502`），横幅又改口成「暂不进入列表」（`:384-386`）——三处说法不一致
2. 「清空列表」声明只清视图，实际把缓冲区一起清了（`:441-456` → `:221-225`），只清视图的 `clear_view()`（`:236-240`）无人调用
3. 删除封禁记录确认框里写了 Markdown `**不会**`，Qt 原样显示星号（`gui/page_bans.py:616`）
4. 封禁记录固定 1000 条上限且无提示，超出静默消失
5. 建议表先 `limit=200` 再筛等级（`gui/page_bans.py:388-393`），未处理事件超 200 条时**旧的高分事件不出现**
6. 设置页切页会覆盖未保存的离线库开关（`gui/main_window.py:530-531` → `gui/page_settings.py:980-983`）
7. 规则页两套保存路径：改完区域规则点「保存名单」不落盘（只有「● 未保存」提示）
8. 封禁失败提示会被 2 秒统计定时器冲掉（`gui/mixins.py:162-166` vs `:236-238`）

### 6.3 界面上看不到的后端能力（14 项，见附录 A）

包括历史访问流水查询、`vacuum`、环境自诊断、`/version`、`/access/batch`、`/banned/{ip}`、限流统计、防火墙规则详情等——**后端能力明显多于界面**。

## 7. 优化建议（按优先级）

### 7.1 P0 — 影响正确性（本轮已修 1 项）

| # | 建议 | 做法 | 代价 | 状态 |
|---|---|---|---|---|
| P0-1 | 规则保存保留不可编辑参数 | `save_config` 改为「现有 ∪ 传入」合并，并在日志里记下保留了哪些键 | 小 | ✅ **已修**（`core/rule_engine.py` + 2 条回归测试 + 恢复 `data/rules.json` 三字段） |

| P0-3 | 上报可信度 | `timestamp` 缺失/偏离服务端 ±N 秒时以服务端为准；IP 覆盖仅在「已配 Key 或可信网段」时允许 | 中（需配置项 + 文档） | 待排期 |

### 7.2 P1 — 体验与可靠性明显欠账

1. **规则级 `level`/`action` 二选一**：要么让引擎真的读（按规则级等级覆盖总分等级），要么从 UI 撤下。现状是「看得见改不动」，比没有更糟。
2. **防火墙操作搬后台线程**：单条解封/一键解封/对账（`gui/page_bans.py:718,743,767`）现在跑在 GUI 线程，PowerShell 超时 30s、一键解封 120s → 界面冻结分钟级。加进度条 + 结果汇总。
3. **确认框统一默认「否」**，红色语义收口：破坏性删除用红描边，「停止服务」降为 outline。
4. **非管理员到期巡检降级**：改为「标记到期 + 明确提示」而不是静默 return，避免账本与防火墙静默偏离。
5. **表格上限显式提示 + 建议表先筛后限**：把 `LIMIT` 下沉到 SQL 的等级过滤之后，或在页脚写「仅显示最近 1000 条」。
6. **修文案 Bug**：暂停/清空的措辞统一；去掉确认框里的 Markdown 星号。
7. **`/rules/reload` 加限流**；API Key 不再写入日志、改常量时间比较。

### 7.3 P2 — 运维能力补齐（按投入产出排序）

1. 事件 / 封禁 / 访问记录导出 CSV（复用 IP 查询页现有实现）
