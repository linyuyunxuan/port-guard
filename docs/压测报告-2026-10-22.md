# PortGuard 稳定性压测报告（2026-10-22）

> 对应 `docs/功能评测与上线建议-2026-10-22.md` 第 4 章「长期稳定性专项」与第 7 章
> 「上线验收清单」。本报告只回答一件事：**7×24 挂着会不会自己出事**。
> 所有数字都可用第 8 节命令复现，不是估算。

## 1. 结论

| 项目 | 结论 |
|---|---|
| 事件页 200 行刷新 | **71 ms**（预算 < 100 ms）✅ |
| 事件页 2000 行刷新 | **669~747 ms** 中位（预算 < 800 ms）✅ |
| 攻击期（200 条/秒）界面 | 60 秒刷 **51 次**、心跳 P95 **19 ms**、最长卡顿 **247 ms**、CPU **16.5%** ✅ |
| 10 条/秒长跑 | CPU 14%，写入丢弃 0，内存出现一次台阶后持平，无增长趋势 ✅ |
| 降级场景（目录只读 / 磁盘满 / 无网） | 三种都「明确失败或退化运行」，无静默假装成功 ✅ |
**一句话**：本轮改造前，攻击期界面会**永久停刷**（60 秒只刷 1 次，之后再也不动）；
现在攻击期仍在每秒刷、卡顿 < 250 ms。这是本轮最重要的一处行为改变。

## 2. 方法与边界

- 工具：`tools/stress.py`（本轮新增，四模式 `refresh` / `flood` / `soak` / `all`）。
- **离屏**（`QT_QPA_PLATFORM=offscreen`）+ **临时数据目录**，不碰真实 `data/`。
- 测前必须做的三件事（否则脚本会挂死或去下载 10 MB 离线库）：
  1. 把所有 `gui.*` 模块的 `QMessageBox` 换成记录器（模态框会阻塞无人值守脚本）；
  2. 关掉 `xdb_auto_sync` / `xdb_sync_on_start`；
  3. `port_watcher.stop_watcher()`。
- 心跳探针：16 ms `QTimer` 记录**实际触发间隔**，最大间隔即用户能感到的最长卡顿。
- 边界：离屏没有真实窗口合成器，绝对值会比真机略好；趋势与相对比较有效。
  RSS 用 `GetProcessMemoryInfo` 读（**必须声明 argtypes**，否则 64 位句柄被截断，
  指标恒为 0 —— 第一版压测就是这么得出「内存零增长」的假好消息的）。

## 3. 事件页单次刷新（刷新档位）

`tools/stress.py refresh`，每档跑 3 次取中位（同一台开发机，CPU 空闲）：

| 条数 | 各次 | 中位 | 预算 | 结论 |
|---|---|---|---|---|
| 200 | 67 / 70 / 79 ms | 71 ms | < 100 ms | 通过 |
| 500 | 137 / 181 / 202 ms | 181 ms | — | — |
| 2000 | 605 / 690 / 786 ms | 669~747 ms | < 800 ms | 通过（个别样本 942 ms，见 §6） |

**本轮为此做的两处优化**（都在 `core/database.py`）：

1. `journal_mode` 只在**不是 WAL** 时才设置。它是**库文件持久属性**，重复设置
   不会带来任何收益，却要拿一次库级锁并回读 header（实测 4~6 ms/次）。
2. 事件列表与「行内按钮的封禁态」**共用一条连接**（`risk_events_page()`），
   省一次建连。建成 WAL 之后 `sqlite3.connect` + 首个语句实测仍要 15~20 ms
   （杀软扫描 + header 读），是 200 行刷新里最大的一块固定开销。

## 4. 攻击期（本轮的核心修复）

场景：已有 2000 条事件，**每秒灌 200 条**风险事件，持续 60 秒，停在事件页。

| 指标 | 改造前 | 只加「慢→降档」 | **再加「攻击信号→先降档」** | 预算 |
|---|---|---|---|---|
| 60 s 内刷新次数 | **1** | 46 | **51** | — |
| 单次刷新均值 | 1367.7 ms | 258.9 ms | **103.8 ms** | — |
| 单次刷新最长 | — | 1658.9 ms | **230.4 ms** | — |
| 心跳 P95 | 18.2 ms | 19.2 ms | **19.1 ms** | < 100 ms ✅ |
| **心跳最长** | 1382.3 ms | 1762.7 ms | **246.5 ms** | < 1.2 s ✅ |
| CPU | 7.9% | 25.2% | **16.5%** | < 30% ✅ |
| 自动暂停 | **true（永久）** | false | **false** ✅ | — |
| 期间写入丢弃 | — | 0 | 0 | 0 ✅ |

### 4.1 为什么原来会永久停刷

旧逻辑只有一条判据：「单次渲染超过 0.8 秒 → 暂停自动刷新，交给用户手动点」。
在攻击期这条判据**必然**成立（2000 行本身就要 0.7~1.6 秒），于是：
第一次刷新慢 → 永久暂停 → 列表冻结。而**攻击期正是最需要盯列表的时刻**。
当时 CPU 只有 7.9%，说明卡的不是资源，是策略。

### 4.2 现在怎么决策（`gui/mixins.py`）

两级信号，都在「渲染之前」判断：

1. **攻击信号（前置）**：单拍（150 ms）新到风险事件 ≥ `EVENTS_BURST_HINT`（20 条，
   约 130 条/秒）→ 先降一档再渲染。为什么不能只看「上次慢了」：那样第一屏必然
   要完整渲染最大档位，实测那一次 1.66 秒（其中含一次 Python 全量 GC），恰好发生
   在用户第一次要看列表的时候。
2. **慢渲染（兜底）**：单次渲染 ≥ 0.8 秒 → 再降一档；**已经是最小档**才暂停自动刷新
   并明示。降档走 `2000 → 500 → 200`，每次只走一级，避免「一下子砍太狠」。

降档会在计数行写明：`共 1420 条事件 · 事件激增，已临时降到最近 500 条`。
用户自己把条数改回去后这句提示自动消失（判据里带 `_downgraded_to`，不需要清理状态）。

**为什么阈值定 20 条/拍**：正常业务流量是个位数/秒（10 条/秒的场景里单拍 1~2 条），
130 条/秒已经差一个数量级。误判代价也小 —— 只是把显示条数临时调小并明说。

## 5. 长时间浸泡

场景：10 条/秒连续灌 300 秒（并在 600 秒的另一轮里复核趋势），停在事件页。

| 时刻 | RSS | 库体积（含 WAL） |
|---|---|---|
| 30 s | 104 MB | 1 MB |
| 120 s | 105 MB | 12 MB |
| 210 s | 105 MB | 38 MB |
| 240 s | **151 MB** | 47 MB |
| 300 s | 152 MB | 47 MB |

- CPU：**13.9%**；写入丢弃：**0 条**。
- 内存：240 s 处出现一次 **46 MB 台阶**，之后完全持平（末三点 151 → 151 → 152 MB）。
  这是**一次性分配**（Qt 表格与 WAL 页缓存扩容），不是泄漏：600 秒那一轮同样在
  47 MB 附近持平。判断依据是斜率，不是绝对值。
- 库体积：稳定在 47 MB 后基本不动（自动 checkpoint + 页复用）。

> ⚠️ **运维提醒**：10 条/秒 ≈ 86 万条/天，库会持续增长。7×24 必须启用
> `app/maintenance.run_daily()` 的每日清理与「保留天数」设置（默认 30 天，
> `log_retention_days` / 访问流水保留一并生效）。本报告的 300 秒里清理还没轮到。

## 6. 未达预算项与取舍（不是 bug）

1. **2000 行档位偶发 942 ms**（超 800 ms 预算约 18%）。原因是该次渲染夹了一次
   Python 全量 GC。**没有为此改动渲染实现**：降到 500 行只要 181 ms，而攻击期
   已经被前置降档挡在 500 行以内，用户实际不会长时间停在这个档位。
2. **`heartbeat_max` 与 `refresh_ms_max` 会一起动**。它们本来就是一回事（刷新在
   界面线程里跑），不必分成两个指标看。
3. **离屏绝对耗时好于真机**。真机上 Qt 栅格化与字体渲染更贵，建议在目标机上按
   §8 命令复跑一次，以真机数字作为验收依据。

## 8. 复现命令

```bash
# 三档刷新（约 30 秒）
QT_QPA_PLATFORM=offscreen envs/portguard/Scripts/python.exe tools/stress.py refresh

# 攻击期 60 秒 @ 200 条/秒（约 70 秒）
QT_QPA_PLATFORM=offscreen envs/portguard/Scripts/python.exe tools/stress.py flood \
    --seconds 60 --rate 200 --rows 2000

# 长跑 300 秒 @ 10 条/秒
QT_QPA_PLATFORM=offscreen envs/portguard/Scripts/python.exe tools/stress.py soak \
    --seconds 300 --rate 10
```

每个模式末尾都有 `RESULT: PASS/FAIL`，可直接当门禁用；`--report <path>` 另存
Markdown 报告。⚠️ 压测**不要与 pytest 并行**（两者都读真实防火墙日志，会互相干扰
出假红），也不要在跑压测的同一分钟里去点界面。
